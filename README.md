# Online Bookstore

A small REST API for an online bookstore built with Java 17 and Spring Boot. It lets users browse books, register and log in, manage a shopping cart, and place and view orders.

## Tech Stack

- Java 17 and Spring Boot
- Spring Web, Spring Data JPA, Spring Security
- H2 in-memory database
- Maven Wrapper

## Getting Started

### Prerequisites

- JDK 17
- The project includes the Maven Wrapper, so a separate Maven installation is not required.

### Run the application

Open a terminal in the project root and run:

```bat
mvnw.cmd spring-boot:run
```

To run the tests first:

```bat
mvnw.cmd clean test
```

The API runs at `http://localhost:8081`. The H2 database is created in memory and resets whenever the application restarts. Five sample books are loaded from `src/main/resources/data.sql`.

## API Reference

All endpoints are under `http://localhost:8081/api/v1`. The examples below use `curl.exe`, which is available on current Windows versions. You can also send the same requests from Postman with `Content-Type: application/json` for requests that have a JSON body.

### 1. List books

**GET** `/books` — returns the available book records. No request body is required.

```bat
curl.exe http://localhost:8081/api/v1/books
```

Example response:

```json
[
  {
    "id": 1,
    "bookTitle": "JAVA",
    "bookAuthor": "James Gosling",
    "bookPrice": 1500.0,
    "booksAvailable": 100
  }
]
```

The database is seeded with `JAVA`, `SPRING BOOT`, `AI BASICS`, `ANGULAR`, and `JAVA SCRIPT`. IDs are generated by the database, so use the IDs returned by this endpoint.

### 2. Register a user

**POST** `/userAuth/register` — creates a user.

```bat
curl.exe -X POST http://localhost:8081/api/v1/userAuth/register -H "Content-Type: application/json" -d "{\"userName\":\"reader1\",\"password\":\"demo123\"}"
```

Request body:

```json
{
  "userName": "reader1",
  "password": "demo123"
}
```

A successful request returns a confirmation message. Usernames must be unique; registering an existing username returns `400 Bad Request`.

### 3. Log in

**POST** `/userAuth/login` — checks the supplied username and password.

```bat
curl.exe -c cookies.txt -b cookies.txt -X POST http://localhost:8081/api/v1/userAuth/login -H "Content-Type: application/json" -d "{\"userName\":\"reader1\",\"password\":\"demo123\"}"
```

Request body:

```json
{
  "userName": "reader1",
  "password": "demo123"
}
```

A successful request returns a confirmation message. Invalid credentials return `401 Unauthorized`. This demo endpoint does not issue an authentication token. It establishes a server-side session. Save the session cookie from login and send it with subsequent protected cart and order requests. The examples below use `cookies.txt` for this purpose.

### 4. View a user's cart

**GET** `/cart/{userId}` — returns the cart items for the given user. Replace `1` with the user ID created in your environment.

```bat
curl.exe -b cookies.txt http://localhost:8081/api/v1/cart/1
```

No request body is required. An unknown user ID returns `400 Bad Request`.

### 5. Add a book to the cart

**POST** `/cart/add` — adds a book to the user's cart. If that book is already in the cart, its quantity is increased.

```bat
curl.exe -b cookies.txt -X POST http://localhost:8081/api/v1/cart/add -H "Content-Type: application/json" -d "{\"userId\":1,\"bookId\":1,\"bookQuantity\":2}"
```

Request body:

```json
{
  "userId": 1,
  "bookId": 1,
  "bookQuantity": 2
}
```

Use an existing `userId` and `bookId`. Quantity must be at least `1`. On success, the API returns `Book Added to Cart Successfully!`.

### 6. View a user's orders

**GET** `/orders/user/{userId}` — returns the orders placed by the given user.

```bat
curl.exe -b cookies.txt http://localhost:8081/api/v1/orders/user/1
```

No request body is required. Use an existing user ID; an unknown user ID returns `400 Bad Request`. A user with no orders receives an empty list.

### 7. Place an order

**POST** `/orders/orderItem/{userId}` — creates an order from the user's current cart and clears that cart after the order is saved. Add at least one item to the cart first.

```bat
curl.exe -b cookies.txt -X POST http://localhost:8081/api/v1/orders/orderItem/1
```

No request body is required. The response contains the created order, including its total, status (`CONFIRMED`) and order items. If the cart is empty, the API returns `400 Bad Request`.

## Suggested end-to-end test

1. Call `GET /api/v1/books` and note a book ID.
2. Register a user with `POST /api/v1/userAuth/register`.
3. Add a book to the cart with `POST /api/v1/cart/add`, using the actual user ID and book ID.
4. Check the cart with `GET /api/v1/cart/{userId}`.
5. Place the order with `POST /api/v1/orders/orderItem/{userId}`.
6. Verify the order with `GET /api/v1/orders/user/{userId}`.

The examples use IDs `1` for illustration. Use the IDs generated in your own run. Since H2 is in-memory, users, carts and orders are cleared when the application restarts.

## Note

This is a learning/demo project. Before production use, review authentication and authorization, securely hash passwords, and add broader automated tests.


## Tests (JUnit 5)

The project includes focused controller unit tests using **JUnit 5** and **Mockito**. The test libraries are declared in `pom.xml` with test scope. Their versions are managed by the Spring Boot parent (`4.1.2`), so no separate JUnit version is pinned.

Test classes are under `src/test/java/com/online/bookstore/controller/`: 

- `BookControllerTest` — returns books and handles an empty result.
- `UserAuthControllerTest` — registration and login scenarios.
- `CartControllerTest` — adding items, stock validation, and missing books.
- `OrderControllerTest` — order-related success and rejection scenarios.
- `OnlineBookstoreApplicationTests` — checks that the Spring application context loads.

Run all tests from the project root on Windows PowerShell:

```powershell
.\mvnw.cmd clean test
```

The controller tests use mocked dependencies to keep them small and fast. They are unit tests; they do not by themselves prove database transaction rollback or the full HTTP/session flow. Those behaviors should also be checked with integration tests if time permits.
